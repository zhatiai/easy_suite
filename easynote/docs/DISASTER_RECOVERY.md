## 三种导出

| 类型 | 内容 | 用途 |
| --- | --- | --- |
| 网页“导出 ZIP” | 当前笔记、回收站、引用文件 | 迁移和普通归档 |
| 网页“导出草稿” | 当前浏览器未同步草稿、已缓存引用文件 | 网络或同步异常时抢救本机内容 |
| `backup.sh` | 完整 D1、所有 D1 记录对应的 R2 对象 | 账号级灾难恢复 |

网页 ZIP 用于笔记迁移；完整账号、会话、AI 令牌哈希、历史版本和删除墓碑由 `backup.sh` 备份。

## 设置中的同步与备份服务器

空站首次访问时还可选择“作为备份节点初始化”，填写来源地址、传输令牌、同步方式与拉取间隔。无需创建本地管理员；同步完成后，使用笔记所属的来源账号和原密码登录。现有站点仍通过设置页管理同步。增量同步保留的本站账号只可查看自身数据。首次拉取失败时暂停定时计划，可在初始化页重新提交，刷新页面可恢复进度。

管理员可打开“设置 → 同步/备份服务器”。Docker 与 Cloudflare 共用传输协议，可在两种部署之间迁移。

1. 在接受连接的对端生成传输令牌，并启用“允许服务器传输”。令牌允许整站读取和写入，仅交给受信任的服务器管理员。
2. 正向同步由本站主动推送，数据流向为本站 → 对端。在“正向同步（主动推送）”填写目标地址、令牌和同步方式。设置推送间隔可启用定时推送。
3. 反向同步由本站主动拉取，数据流向为对端 → 本站。在备份节点的“反向同步（主动拉取）”填写主节点地址和令牌，即可由备份节点拉取主节点知识库。设置拉取间隔可启用定时拉取。
4. 覆盖式同步将目标整站替换为来源数据。增量同步以相同主键识别记录，来源端优先，保留目标端独有记录。账号名相同但 ID 不同会中止并提示冲突。来源笔记和文件夹的分享状态以来源为准，永久删除笔记的墓碑在两端合并，防止旧副本复活。其他来源缺失记录作为目标独有数据保留。
5. 输入 `OVERWRITE` 确认写入目标，再保存计划或立即执行。推送、拉取各自保存方式与间隔，`0` 关闭该方向的定时任务。已有配置默认沿用覆盖式推送，拉取定时默认关闭。

增量任务先比较记录主键与摘要，正文相同时仅传输引用信息。附件比较所属账号、ID、SHA-256、大小及目标对象状态，跳过已有相同文件。提交时在本地暂存库合并目标独有记录，再使用同一事务发布完整结果。两种方式均保留目标的连接配置，完成后目标浏览器会话失效并重建离线库。增量同步仍需暂存完整元数据，附件只为新增及变化内容占用额外暂存空间。

两端代码指纹必须完全一致。指纹根据源代码、迁移、静态资源、运行脚本、依赖锁和构建配置计算。连接和提交阶段均校验指纹。修改代码后需重新构建并更新两端。

整站传输包含全部账号、密码验证器、注册设置、笔记与文件夹、历史、分享、集成令牌、墓碑、同步日志及全部可用附件。目标浏览器会话和临时 OAuth 授权码在提交时失效。再次登录时，浏览器清理上一份数据的离线镜像和草稿，其他打开的标签页随数据代次变化重新加载。执行前请等待草稿保存完成。

任务由持久化 Durable Object Alarm 执行。Docker 将其状态保存在 `/data/state/do`。连接配置、传输凭据、任务记录与计划按服务器独立保存。接收令牌仅生成时显示原文，设置接口返回已配置状态。

传输期间两端进入维护状态，业务 API 返回 `503`。目标先接收暂存表与独立对象前缀，逐个校验附件大小和 SHA-256，再在一次数据库事务中替换整站数据。提交前失败时原数据仍可使用。提交响应丢失时依据数据代次幂等重试。中断后维护租约最长十分钟到期，后台回收暂存数据与旧对象。目标需为暂存数据库、附件及原数据预留空间，峰值接近两份数据加 SQLite 日志，完成后回收旧数据。

传输地址应为可由发起服务器访问的 HTTPS 源地址，可包含端口。重定向被拒绝。私有网络可使用受信任证书与内部 DNS。选择能够发起连接的一端执行任务。Cloudflare Worker 的 fetch 无法直连 IP，需使用域名；主站无法连接 Docker 节点时，可在 Docker 节点配置反向拉取 Cloudflare 主站域名。

Docker 出站 HTTPS 使用镜像内 `ca-certificates` 提供的 Linux 公共 CA 信任库。对端使用私有 CA 或新 CA 时，可将受信任 CA 的 PEM 文件只读挂载到容器，并设置 `NODE_EXTRA_CA_CERTS` 为容器内路径；运行用户必须有读取权限。Cloudflare 对端需使用平台认可的证书链。

## 远程授权

所有带 `--remote` 的备份、预检、恢复和密码重置命令都要求交互式终端，并在每次运行时隐藏输入 Cloudflare 自定义 API Token。目标账号范围内需要 Workers Scripts (Edit)、D1 (Edit) 和 Workers R2 Storage (Edit)；首次自动部署还需要 Account Settings (Read) 以发现目标账号，使用 Custom Domain 时再添加目标 Zone 的 Zone (Read) 和 Workers Routes (Read)。

脚本在每次远程操作时通过终端隐藏读取 Token，Token 生命周期限定在本次运行。`wrangler.deploy.json` 保存 Account ID、Worker 名以及 D1/R2 资源标识。灾备和部署使用 Cloudflare API Token，EasyNote AI 集成令牌用于 MCP。

## 创建备份

生产备份：

```bash
bash backup.sh --remote
```

本地开发数据：

```bash
bash backup.sh --local
```

可使用 `--output DIR` 指定新的备份目录。脚本执行：

1. 通过 Wrangler 导出全部 D1 业务表 SQL；可重建的 FTS5 搜索索引不进入备份。
2. 从该 SQL 快照读取所有状态为 `ready` 的私有文件记录。
3. 按附件记录的 `storage_key` 下载 R2 对象，旧数据回退到 `<user_id>/<file_id>`。
4. 对照 D1 中的大小和 SHA-256 逐个校验。
5. 写入带数据库、Schema 基线和对象校验值的 `manifest.json`。

备份包含密码验证器、会话哈希和 AI 令牌哈希，目录权限设为仅当前用户可读写。应将备份复制到加密、离线且有独立保留策略的位置。

## 恢复预检

先创建全新的 D1 和 R2 资源，并写入独立的 `wrangler.deploy.json`，恢复目标保持为空。

```bash
bash restore.sh /path/to/easynote-backup --remote --check
```

预检只读执行以下检查：

- 清单、D1 SQL、当前 Schema 基线和全部 R2 对象哈希一致。
- 目标 D1 尚未初始化，或已有完整但无数据的 EasyNote Schema。
- 目标 D1 的账号、笔记和文件记录数均为零。
- 备份将写入的每一个 R2 Key 在目标桶中都不存在。

全部条件通过后才能进入正式恢复。

## 执行恢复

```bash
bash restore.sh /path/to/easynote-backup --remote
```

输入确认文本后，脚本会在需要时建立当前数据库结构，重新检查目标为空，先恢复 R2 对象，再导入 D1 数据。笔记导入时会自动重建全文索引。中途失败时保留输出用于排查，并对新的空资源重新执行恢复。

恢复后应立即：

1. 运行 `bash reset-password.sh --remote`。
2. 重新创建仍需使用的 AI 令牌。
3. 登录网页，抽查笔记、历史版本、图片和附件。
4. 再创建一份新的灾备并执行 `--check`。

## 恢复演练

正式上线前至少完成一次隔离恢复：

1. 创建临时 D1 和私有 R2 桶。
2. 为临时资源生成独立配置。
3. 对最新备份运行恢复预检。
4. 执行恢复并部署临时 Worker。
5. 核对 D1 各表数量、R2 对象数量及代表性文件。
6. 完成后删除临时 Worker、D1 和 R2。

Cloudflare 资源由管理员显式创建、删除和切换；远程备份按管理员设定的周期执行并离线保管。
